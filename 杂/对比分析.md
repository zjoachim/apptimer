# AppTimer v2 vs Tai 深度对比分析

## 一、技术栈对比

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **语言** | Python 3.14 | C# (.NET Framework 4.8) |
| **UI 框架** | pywebview + Vue 3 + Tailwind CSS + ECharts | WPF (XAML + MVVM) |
| **前端构建** | Vite 6 | 无（原生 WPF） |
| **数据库** | JSON 文件 | SQLite (Entity Framework 6) |
| **进程检测** | ctypes 调 Win32 API | P/Invoke 调 Win32 API |
| **浏览器通信** | 无 | WebSocket (Chrome 扩展) |
| **依赖注入** | 无 | Microsoft.Extensions.DI |
| **打包** | PyInstaller → 单 exe | .NET 编译 |
| **开机自启** | 注册表 Run 键 | Task Scheduler (管理员权限) |
| **图标提取** | 无 | 自定义 Iconer (ExtractIcon) |
| **Excel 导出** | 无 | Npoi.Mapper + CsvHelper |
| **PDF 导出** | fpdf2 | 无 |
| **JSON 库** | 内置 json | Newtonsoft.Json |

## 三、核心功能对比

### 3.1 窗口检测机制

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **检测方式** | `GetForegroundWindow` 主动轮询 | `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 被动事件 |
| **轮询间隔** | 2 秒 | 事件驱动（实时） |
| **进程信息获取** | 三级降级：OpenProcess → LimitedInfo → Toolhelp32Snapshot | OpenProcess + QueryFullProcessImageName |
| **UWP 支持** | 无特殊处理 | 有：EnumChildWindows 获取真实子进程 |
| **系统组件过滤** | 硬编码忽略列表 | 窗口类名 + 进程名判定 |
| **窗口标题获取** | GetWindowTextW | GetWindowText |
| **图标提取** | 无 | 有：ExtractAssociatedIcon |

**评价**：Tai 的事件驱动方式更高效（不浪费 CPU 轮询），UWP 支持更完善。AppTimer 的三级降级策略在权限受限时更健壮。

### 3.2 计时精度

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **最小计时单位** | 2 秒（轮询间隔） | 1 秒（Timer 精度） |
| **时间记录** | 浮点数秒 | 整数秒 |
| **会话记录** | 包含开始/结束 ISO 时间 | 包含开始/结束时间 |
| **数据拆分** | 按天存储 | 按天 + 按小时双维度存储 |

**评价**：Tai 有更细粒度的小时维度数据，便于分析使用时段分布。AppTimer 的 2 秒轮询可能导致短暂切换丢失。

### 3.3 数据存储

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **存储格式** | JSON 文件 | SQLite 数据库 |
| **存储位置** | `{Desktop}\程序使用记录\` | `{运行目录}\Data\data.db` |
| **数据结构** | 按日期文件夹 + 累计文件 | 统一数据库，8 张表 |
| **查询能力** | 需加载全量 JSON | SQL 查询，支持复杂聚合 |
| **并发安全** | 无锁（单线程写入） | 读写锁机制 |
| **数据迁移** | 文件复制 | 数据库文件复制 |
| **可读性** | 高（JSON 可直接阅读） | 低（需 SQLite 工具） |
| **数据保留** | 可配置（默认 60 天自动清理） | 无自动清理 |

**评价**：Tai 的 SQLite 方案更适合大量数据和复杂查询。AppTimer 的 JSON 方案更简单直观，但随数据增长性能会下降。

### 3.4 浏览器网站追踪

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **实现方式** | 窗口标题关键词匹配 | Chrome 扩展 + WebSocket |
| **追踪精度** | 仅当前活跃标签的标题 | 每个标签页独立追踪 |
| **数据粒度** | 进程名 + 关键词分类 | 完整 URL + 标题 + 图标 + 时长 |
| **支持浏览器** | 任何浏览器（通过窗口标题） | Chrome（可扩展到其他 Chromium） |
| **分类方式** | 硬编码关键词规则 | 用户手动分类 + 独立网站分类表 |
| **心跳保活** | 无 | 10 秒心跳，自动重连 |
| **睡眠同步** | 无 | 接收 Tai 的 sleep/wake 消息 |

**评价**：Tai 的浏览器追踪是真正的标签页级追踪，精度远超 AppTimer 的窗口标题匹配。但 AppTimer 的方案无需安装扩展，兼容所有浏览器。

### 3.5 空闲/睡眠检测

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **检测方式** | `GetLastInputInfo` 单一指标 | 鼠标位置 + 键盘 + 声音 + 电源事件 |
| **检测周期** | 每 2 秒（跟随主循环） | 每 5 分钟 |
| **阈值** | 可配置（默认 120 秒） | 多级阈值（30秒~10分钟） |
| **声音检测** | 无 | 有：Core Audio API 检测系统声音 |
| **电源事件** | 无 | 有：监听休眠/恢复事件 |
| **远程桌面** | 无 | 有：监听 SessionSwitch 事件 |
| **唤醒方式** | 键盘/鼠标活动 | 键盘钩子 + 鼠标钩子（双击/滚轮） |

**评价**：Tai 的睡眠检测维度更丰富，能更准确判断用户是否真正在使用电脑。AppTimer 的方案简单但可能误判（如用户看视频时无键盘鼠标操作）。

### 3.6 分类系统

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **分类方式** | 手动 + 窗口标题关键词自动分类 | 手动 + 可执行文件路径自动匹配 |
| **自动分类规则** | 硬编码在 `SITE_RULES` | 用户配置目录匹配规则 |
| **网站分类** | 无独立分类 | 有：独立的 WebSiteCategoryModel |
| **分类维度** | 工作/学习/娱乐/社交/开发/设计/其他 | 用户自定义 |
| **目录匹配** | 无 | 支持按可执行文件所在目录自动分类 |

**评价**：Tai 的分类更灵活，支持用户自定义规则和目录匹配。AppTimer 的自动分类依赖硬编码关键词，扩展性差。

### 3.7 导出功能

| 维度 | AppTimer v2 | Tai |
|------|-------------|-----|
| **PDF** | 有（fpdf2，含表格和进度条） | 无 |
| **Excel** | 无 | 有（xlsx + csv） |
| **CSV** | 有（当日 + 累计） | 有（通过 CsvHelper） |
| **网站数据导出** | 无 | 有（独立导出） |
| **编码** | UTF-8 BOM（Excel 友好） | 默认编码 |

**评价**：各有优势。AppTimer 的 PDF 报告适合分享，Tai 的 Excel 导出适合数据分析。

### 3.8 UI 功能

## 五、优劣势总结

### AppTimer v2 优势
1. **轻量简单**：代码量少，易于理解和维护
2. **部署简单**：单 exe，无需安装运行时
3. **兼容性好**：无需浏览器扩展，支持所有浏览器
4. **PDF 导出**：直接生成可分享的报告
5. **卸载功能**：内置卸载流程
6. **Python 生态**：易于扩展和集成第三方库

### AppTimer v2 劣势
1. **浏览器追踪粗糙**：仅窗口标题关键词匹配
2. **无睡眠检测**：仅简单的空闲检测
3. **数据存储弱**：JSON 文件随数据增长性能下降
4. **无关联进程**：无法处理多进程应用
5. **无图标提取**：应用列表缺少视觉标识
6. **计时精度低**：2 秒轮询可能丢失短暂切换

### Tai 优势
1. **浏览器追踪强大**：Chrome 扩展 + WebSocket，标签页级精度
2. **睡眠检测完善**：多维度检测（鼠标+键盘+声音+电源）
3. **数据存储健壮**：SQLite + EF6，支持复杂查询
4. **架构清晰**：分层 + MVVM + DI，可扩展性强
5. **功能丰富**：关联进程、白名单、正则过滤、图标提取等
6. **计时精度高**：事件驱动 + 1 秒精度 + 小时维度数据

### Tai 劣势
1. **复杂度高**：代码量大，学习曲线陡
2. **部署依赖**：需要 .NET Framework 4.8 运行时
3. **浏览器限制**：仅支持 Chrome（需安装扩展）
4. **无 PDF 导出**：缺少可直接分享的报告格式
5. **数据位置**：存在运行目录，卸载可能丢失数据
6. **管理员权限**：开机自启需要管理员权限

## 六、可借鉴的 Tai 特性

按优先级排序，以下是 AppTimer v2 可以从 Tai 借鉴的特性：

### 高优先级（显著提升体验）
1. **事件驱动窗口检测**：用 `SetWinEventHook` 替代轮询，更高效且不丢失切换
2. **UWP 应用支持**：处理 `ApplicationFrameHost` 的子窗口枚举
3. **应用图标提取**：自动提取 exe 图标，提升 UI 视觉效果
4. **小时维度数据**：按小时记录使用时长，支持时段分析

### 中优先级（功能完善）
5. **关联进程**：支持多进程应用同步计时（如 Office 套件）
6. **正则忽略列表**：更灵活的过滤规则
7. **应用别名**：自定义显示名称
8. **目录匹配分类**：基于可执行文件路径的自动分类

### 低优先级（锦上添花）
9. **声音检测**：判断用户是否在看视频/听音乐
10. **电源事件监听**：检测休眠/恢复
11. **雷达图**：多维度数据可视化
12. **月视图**：日历热力图展示使用习惯

## 七、实现建议

如果要在 AppTimer v2 中实现 Tai 的核心优势特性，建议按以下顺序：

### 阶段一：窗口检测优化
- 将 `window_detect.py` 的轮询改为 `SetWinEventHook` 事件驱动
- 添加 UWP 应用支持（`EnumChildWindows`）
- 添加应用图标提取（`ExtractAssociatedIcon`）

### 阶段二：数据模型升级
- 考虑从 JSON 迁移到 SQLite（或至少添加小时维度）
- 添加关联进程配置
- 添加正则忽略列表

### 阶段三：浏览器追踪（可选）
- 开发 Chrome 扩展
- 添加 WebSocket 服务器
- 实现网站分类系统

### 阶段四：睡眠检测增强
- 添加声音检测（需要 Core Audio API）
- 添加电源事件监听
- 优化空闲检测逻辑
